## 2026-11-13 (S5-5b: the silent-run watchdog)

- **`withSilenceWatchdog`** wraps a runtime's event stream in the run loop. If no event arrives for the threshold it calls the runtime's `cancel`, yields one `error` event of the new kind **`silent`** ("The run produced no output for N seconds, so it was stopped. It was most likely stuck.") and ends, without waiting for the hung source. Silence is counted from the last event, so a long run that keeps talking is never touched; the 15 minute run timeout is unchanged and separate.
- **Default 5 minutes, a setting:** `LoopDeps.silenceMs`, set from `RUN_SILENCE_MINUTES` in the server (0 turns it off). The local model on this CPU takes a minute or two for a first answer, so 5 minutes leaves room; an agent that needs longer should raise it.
- **A silent run is worth another try,** so `failureClass` calls it transient: it goes through the S3-2 retry plan (backoff, then the fallback model) like a network error, and only blocks the task if those fail too. A hang past the full timeout stays permanent. Tested with a runtime that hangs on its first attempt and works on its second.

## 2026-11-13 (S5-5a: low-trust agents)

- **`trust: low` in the role file** (left out means standard; any other value is refused), stored as `agents.trust` (migration 0036). The scout templates (`scout`, `demand-scout`, `problem-scout`) set it by default because they read posts and pages anyone can write.
- **Contained in the server, not asked to behave.** (1) **Tools:** the run token of a low-trust run carries its trust and a list of allowed `os` tools: the base five (`get_task`, `comment`, `complete_task`, `block_task`, `ask_founder`) plus the tools its template's plugins name. `callOsTool` refuses anything else as an unknown tool whatever the autonomy level, `tools/list` shows only the list, and **a low-trust token with no list can call nothing** (fail closed). (2) **Permissions:** the narrower of the template and the trust level wins: a low-trust agent gets no write, no shell and no subagents in every render target and in the run's tool lists, even if its template allows them; reading stays, because reading hostile input is its job. Its role file and config live outside its `work/` folder, which is cleaned before each run, so it cannot rewrite them. (3) **Data, not instructions:** in `get_task`, anything a low-trust agent wrote is returned inside a label saying it is data written by a low-trust agent and not to be acted on. Founder and standard-agent comments are returned as they are.
- **Not done in this task:** labelling low-trust output in the other places an agent can read it (the brief's narrative, lead notes). Those are written by specific tools (`add_brief_note`, `add_lead`) that scouts do not have, so there is nothing to label yet; any new tool that lets a low-trust agent write text another agent reads must label it too.

## 2026-11-13 (S5-4: approved DMs, one at a time)

- **`dms` table** (migrations 0034, 0035) and the `os` tool **`propose_dm`** (autonomy 2). The input is one account, one lead, one handle and one text, strict: a list, an array or an unknown field is refused, and nothing else can create a DM (there is no route to; a test asserts `POST /api/dms` is 404 and that no tool has a name like bulk, follow, like, broadcast or mass). Rule 6 is therefore a property of the shape, not of a prompt.
- **A DM is never the first cold touch.** The lead must be in stage `contacted` (an approved email went out), `replied`, `qualified` or `won`; `new`, `lost` and `do_not_contact` are refused with the reason. This is how "not written to first by a person" is read, since the only way a lead becomes `contacted` is a person-approved email. The recipient handle is compared without `@` or case against the suppression list, and the lead's email and its domain are checked too. The text goes through the same claims, price and approved-link rules as a post, with the platform's length (X 10,000, Instagram 1,000).
- **`dm.send` is the third executor kind.** Same claim-once, kill switch, recheck-at-send and never-retry rules as email and posts. New here: **one at a time per account.** Under a per-account lock, an approval is held (still `approved`, reported to the gate with when to try again) if the account's daily limit is used (the smaller warm-up limit while warming up; the limit counts DMs sent or going) or if another DM from that account was claimed or sent less than the gap ago (default 90 seconds, `dmGapMs`). Two approved DMs asked for at once therefore go out one after the other, in the order the gate asks. The gap counts from when a send was claimed, so a DM in flight blocks the next.
- **Outbox only for now:** the DM transport writes `DATA_DIR/outbox/dms/<approval>.json`. A browser DM path would need its own recipes and a real account to check them against, so it waits; the posting browser driver is not reused for DMs.
- **Approval cards:** a person may edit only the `text` of a DM approval, as with posts; decisions and expiry move the `dms` row (`approved`, `rejected`, `expired`); restart recovery marks a DM left sending as failed with an item and never sends it again.

## 2026-11-13 (S5-3: browser profiles)

- **Three new columns on `channel_accounts`** (migration 0033): `transport` (`outbox` default, or `browser`), `browser_profile` (the folder name, null until a person has logged in) and `session_state` (`none`, `valid`, `expired`, with a checked-at time). A profile folder is `DATA_DIR/browser-profiles/<account id>`: the id is validated to letters, digits, dashes and underscores so it can never point elsewhere, and the folder is outside the repo by construction.
- **Logging in is by hand, once:** `pnpm run browser:login <handle or id>` opens a visible browser (Playwright on an installed Edge by default; `CONCLAVE_BROWSER_CHANNEL` or `CONCLAVE_BROWSER_PATH` change it, nothing is downloaded) on the profile at the platform's login page and waits for you to close it. Then the account has a profile and a valid session. The OS never sees a password; nothing but the browser's own folder is written. Logging in does **not** switch the account on.
- **Switching on is a separate, deliberate step:** `POST /api/browser/accounts/:id/transport {"transport":"browser"}` is refused (409, saying what to do) until the account has a profile and a valid session, and is audited. `GET /api/browser/accounts` lists each account's profile, session and transport; `POST .../session` lets a person mark a session expired or valid.
- **The executor chooses by the account:** the browser transport only for an account set to it, the outbox otherwise. A browser account whose session is not `valid` is not opened at all: the post waits (`needs_login`) with the one `session_expired` item. A driver that finds the login gone also marks the session `expired`. Logging in again closes the item. If an account is set to the browser and the server has no browser transport, the post is refused with that reason.
- **The Playwright driver is written but UNVERIFIED** (and says so at the top of `browser/driver.ts` and in the test): it has recipes for X and LinkedIn written from how the sites looked, and has never met a logged-in account. The flow is tested against a fake page: it goes to the compose address, treats a login-page address as an expired session before typing anything, fills the text, presses Post exactly once, waits for the address to change, takes a screenshot, and always closes the browser. Instagram text posts are refused with a plain reason, because Instagram needs an image. The first real post must be watched with `BROWSER_HEADLESS=0`; this is in NEEDS-YOU.

## 2026-11-13 (S5-2: the post executor and its transports)

- **One executor registry, two kinds.** `createExecutors` looks up the approval's kind and runs `executeEmail` or the new `executePost`; recovery and "send the approved ones" now cover both. The gate needed no change.
- **`executePost` follows the email executor's rules:** claim once (`approved` to `executing`, with the post row `publishing`), kill switch first, every check again against the world as it is now (the account exists, is a posting account and is `ok`; the text passes the same length, claims and link rules as at proposal), publish the exact approved text (or the founder's edit of it) once, never retry. Success records `{ref, url, transport, screenshot?}` on the approval and the url and time on the post. Any other failure marks the approval and post failed and raises an `executor_failed` item saying it was not retried. A post left `executing` by a stop is marked failed with a "may or may not have been published" item and is never published again.
- **Two transports.** `outbox` (default, in `createOutreach`) writes `DATA_DIR/outbox/posts/<approval>.json`; nothing leaves the machine. `browser` publishes through a small `BrowserDriver` interface and saves the screenshot to `DATA_DIR/screenshots/<approval>.png`, storing the key and the final address on the approval (SPEC 8). The Playwright driver itself comes with the profiles in S5-3; the transport is tested against a fake driver.
- **An expired login is not a failed publish.** The driver throws `SessionExpiredError` before anything is posted; the executor puts the approval back to `approved` (post `approved`), raises one `session_expired` item per account however often it is tried, and returns `needs_login`. "Send the approved ones" publishes it once the login is fixed.
- **Approval decisions now reach the post row:** approving moves a `proposed` post to `approved`, rejecting to `rejected`, expiry to `expired`. A person may edit only the `text` of a post approval (not the account); the edit is validated and re-checked at publish time, and the post row ends with the text that went out.
- **No per-account daily cap for ordinary posts yet:** each post is its own approval, which is the control. Caps apply to DMs (S5-4), where rule 6 asks for them.

- **`posts` table** (migrations 0031, 0032: forced row-level security, composite keys to the channel account and the approval) and the `os` tool **`propose_post`** at autonomy 2, like `propose_email`. It queues an approval of kind `post.publish` with the platform, handle, account and exact text, writes a `proposed` post row, tells the approval gate, audits `post.proposed`, and publishes nothing. A rejected, expired or cancelled earlier proposal does not block a new one, which gets its own approval key. The database enforces it with a partial unique index.

## 2026-11-13 (S4-7: the scout template, the signal tools and the paused rooms)

- **A scout works on items it is handed, not on the open web.** The in-process runner has no web, file or shell tool (rule 10), so the `scout` template has every one of those permissions on deny and its skills say the items are in its task (source, address, author, text). Something has to put them there: a source connector (a scraper or an API, within each site's terms) is the founder's to set up and is parked in NEEDS-YOU. Until then a scout can be given items by hand in a task, which is also how the trial task and the end-to-end test feed it. This is the honest reading of "scouts only read through an approved scraper or API".
- **Two `os` tools, `add_signal` and `score_signal`, both level 1.** `add_signal` takes kind, source, the exact address, author and a short quote, refuses a missing or non-web address, a bad kind and any unknown field, strips control characters and cuts the quote to 1,000 characters, and tells the scout when the address was already recorded. `score_signal` takes a 0 to 100 score and a reason; 60 or more marks the signal **qualified**, which is what the morning list counts; a lower score leaves it new for a person. It refuses a signal a person already promoted or dismissed. There is deliberately **no** tool to promote, dismiss or contact: those stay with a person (rules 1 and 6).
- **A post that reads like orders to an agent is kept, flagged, and changes nothing** (the draft task said "refuses"; refusing would lose a real request that happens to say "ignore my last message"). A few patterns (ignore/disregard your instructions, "you must now call/send/post", system-prompt talk, tool names, tags like `<system>`) set the signal's `reason` to say so and the tool reply tells the scout not to act on it. The test checks no task, lead or approval appears as a result.
- **The plugin `signals-kit`** (skills `find-signals` and `score-signal`; its tool list is checked against the server) and **three templates**: `scout` (runs hourly on `openai-agents`/`local-worker`, autonomy 1, escalation to Claude through `fallback_runtime`, `output_check: non-empty`, a budget of $2 a month that only escalations to Claude can spend, because a budget of zero means nothing is allowed), `demand-scout` (room 9) and `problem-scout` (room 6).
- **"Configured and paused":** a template can say `start_paused: true`, which the role file carries and the company sync honours when it first adds the agent (status `paused`, kept as it is afterwards; a retired agent comes back to the status the role file asks for). The two room templates set it. A paused agent is not woken by the heartbeat and its `os` tools do not exist (the store already treated any non-active agent as level 0). Turning one on is setting its status to active.
- **Template defaults gained `fallback_runtime`, `fallback_model` and `start_paused`,** and the role-file schema gained `start_paused`.

## 2026-11-13 (S4-6: the signals table and its API)

- **Table `signals`** (migrations 0029, 0030: forced row-level security, `workspace_id`, composite foreign keys to departments and leads), shaped like SPEC 11 with these changes: ids are uuids as everywhere else; `found_by` (`founder` or `agent:<key>`), `reason` (why it was qualified or dismissed) and `updated_at` were added; `opportunity_id` was left out until a task needs it (opportunities exist, nothing links to them yet); kind, status and score are database checks as well as validated in code.
- **One signal per web address, in a normal form:** no fragment, no tracking parameters (`utm_*`, `fbclid`, `gclid`, `mc_*`, `igshid`), parameters sorted, no trailing slash, no `www.`, lower-case host. Only http and https are accepted, so `javascript:` and `file:` addresses are refused. Adding the same address again returns the one already stored (200, `duplicate: true`); the insert is `on conflict do nothing`, so two scouts finding it at once still make one.
- **Status moves:** new, then qualified (with a score 0 to 100 and a reason) or dismissed; a dismissed signal is reopened by qualifying it again; promoted is final. Promoting a dismissed signal is refused (409) until it is re-qualified.
- **Promote goes through the same `ingestLead` as every other lead,** so suppression and duplicate rules still apply. The lead's source is the signal's address, which makes it verified (it has a source, SPEC 15) and eligible for a campaign; its name is the author handle, its notes the excerpt, the address and the reason. Promoting twice returns the same lead. A signal alone never contacts anyone.
- **API:** `GET /api/signals` (filters `status`, `kind`, `limit`), `GET /:id`, `POST /` (a person adds one by hand; scouts use the `os` tool in S4-7), `POST /:id/qualify`, `/dismiss`, `/promote`. Each decision is audited (`signal.added`, `.qualified`, `.dismissed`, `.promoted`).

## 2026-11-13 (S4-5: the other engine, for plan limits and escalation)

- **One new role-file field, `fallback_runtime`,** next to the existing `fallback_model`: the other engine this agent may use. It needs a `fallback_model`, and that alias must list the fallback runtime (without `fallback_runtime` the fallback model is for the same runtime, as before). Stored in `agents.fallback_runtime` (migration 0028). The same pair serves both directions: a Claude scout names the local model, a local scout names Claude.
- **While an agent's runtime is paused for a plan limit,** if its role names another engine that is not itself paused, the run starts there instead (rendered folder for that engine, run row says which runtime and model it used, a `reroute` event with the reason `paused`). With no other engine, or both paused, nothing changes from S3-3: not runnable, the task stays queued. So scouts and triage (given a local fallback) keep working and writers (given none) wait, exactly as the spec says; which agents move is a property of their role files, not of the code.
- **The same switch serves the retry fallback (S3-2) and the escalation after a failed check (S3-5):** when either lands on the fallback model and that model is on another runtime, the run moves engine mid-run (`reroute` reasons `retry` and `escalate`). A session belongs to one engine, so the run starts that engine fresh and never resumes the other's session id; the repair text already carries what was wrong. Escalation is still once, and a second failure still blocks the task.
- **A plan limit is recorded against the engine the run was on when it hit the limit,** not the one the agent normally uses (it previously used `agent.runtime`).
- **The Health screen** has a "Moved to another engine" part from `reroutes` in the overview (agent, from, to, why, when; last window).

## 2026-11-13 (S4-3: the skill loader)

- **The in-process runner reads the agent's rendered folder:** `INSTRUCTIONS.md` (standing rules and role, written by the S4-4 render target), then the per-run context, then a "Skills" part listing each skill as `name: description` (taken from the skill's own front matter), never its text. If the folder has skills the model gets one extra tool, `load_skill(name)`; with none it gets no such tool.
- **What `load_skill` can reach is exactly the agent's `.skills` folder.** A name must be lower-case words and hyphens (so no `/`, `..`, drive letters or empty names), the file must resolve with its real path inside the folder (so a link or junction that leads out is not a skill, and is not listed either), and it must be a file. A refusal comes back to the model as a plain sentence ("You do not have a skill called ..."), not a crash, so a small model that guesses a name can recover. Tested with traversal names, an absolute path, a junction to a folder holding a planted secret, and a folder with no SKILL.md.

## 2026-11-13 (S4-2: the openai-agents runtime)

## 2026-11-13 (S3-9: the daily backup)

- **The dump is our own format, because the embedded Postgres ships without `pg_dump`** (checked: its bin folder has initdb, pg_ctl and postgres only). A backup is one gzip file of JSON lines in `DATA_DIR/backups/`, `backup-<day>-<time>.jsonl.gz`: a header (format, time, each table with its row count and columns), the rows in batches, and an end line with a SHA-256 of everything before it. It reads every table in `public` and `auth` in one read-only repeatable-read transaction, as the owner role (which bypasses row-level security, so it sees every workspace; the request role cannot). That is a snapshot, so the dump is consistent while the server runs.
- **A failed dump cannot hurt the old ones:** it is written to `.tmp`, checked by reading it back, and renamed into place only then. Only after a good one are the older files pruned to the newest 14.
- **Restore only fills an empty database.** It checks the file first (unpacks, checksum, row counts) before it opens the database; then refuses if any table holds a row, except the single bootstrap workspace a new database starts with, which it replaces with the backup's own. "The OS never deletes a database that holds data" holds: the only thing it removes is that empty bootstrap row. Columns must match the backup's, so restore into the same version. Foreign keys form loops (tasks and runs point at each other), so tables load in dependency order and, where a loop cannot be ordered, an optional link is left empty on the first pass and filled in on the second. Sequences are set to the highest loaded value. Tested by restoring a real dump into a second, fresh database and comparing.
- **The failure item is raised once:** a `backup_failed` action item, its text updated on each further failure and closed by the next good backup. After a failure the daily job waits an hour, not a minute, before trying again.
- **The company commit** (`git add` then `git commit -- <company folder>`) commits only that folder and only when `git status` shows a change there, so other staged work stays staged. It never pushes. It is skipped for a folder outside any git repository, uses a placeholder identity only if git has none, and `COMPANY_BACKUP_COMMIT=0` turns it off. Heads-up: in this repo `company/` is tracked on `dev`, so a running server will commit changes to it on whatever branch is checked out.
- **Commands:** `pnpm run backup` (now) and `pnpm run backup:restore <file>` (with DATA_DIR pointing at a new folder). Schedule: after `BACKUP_TIME` (default 02:30, company time zone), once a day, started from the minute ticker; a backup already made today (before a restart) counts.

## 2026-11-13 (S3-6: circuit breakers)

- **One breaker per os tool (`os:<tool>`), in the `circuit_breakers` table.** Three failures in a row open it for 5 minutes; calls are then refused at once, with a message the agent can act on ("temporarily unavailable ... carry on without it or block your task"), and the tool is not asked. A refused call is not counted. After the cooldown the first call goes through and the breaker closes; three fresh failures are needed to open it again. A success resets the count.
- **A failure is a tool that broke, not a tool that said no.** An exception that is not a `ToolError` counts; a `ToolError` (bad input, "not in progress") means the tool worked and counts as a success. Otherwise an agent sending bad input three times would switch a tool off for everyone.
- **Only real tool names get a breaker**, so an agent inventing names cannot fill the table.
- **One action item per opening** (`breaker_open`, body starts `breaker: <key>`), closed when the breaker closes. A person can reset early with `POST /api/breakers/:key/reset` (404 if it is not open); `GET /api/breakers` lists all. Opening and closing are audited.
- **Scope for now is the os tools.** Connectors (the outbox transport, lead sources) are not behind a breaker yet because none is live; each gets one with the same class when it is connected. The Health screen (S3-7) shows breakers and the reset.

## 2026-11-13 (S3-4: budgets)

- **The ledger is the runs table.** Before every run, what the agent's runs have cost this calendar month (this machine's month) is compared with its monthly_budget_usd. At or over it, the agent starts nothing and no task is taken, and the tasks stay queued. ## 2026-11-13 (S3-3: plan-limit handling)

- **A plan limit pauses the runtime, not the work.** When a run ends on a usage limit, the runtime it ran on (Claude Code, OpenCode...) is paused: no agent on it starts a run or takes a task until the reset, agents on other runtimes carry on, and the task that hit the limit goes back to todo with its session kept instead of being blocked (it is not the task's fault, so no person need look at it). One pause per runtime at a time, in a runtime_pauses table (migrations 0024, 0025); a second limit while paused only keeps the later reset.
- **One action item, closed by itself.** The first limit raises a single item ("Claude Code is paused: its plan limit was reached") however many agents hit it; it closes when the pause lifts, whether at the reset, early by a person, or by the system.
- **The reset time comes from the runtime's own message** when it gives one (Claude Code writes it as a Unix time after a bar). With none, or one already past, or more than a day away, the pause is five hours, the length of a plan window. That default is my choice and is logged here.
- **It lifts itself.** The ticker lifts every pause whose time has come, closes the item and wakes the agents that have tasks waiting. A pause whose time has passed is also ignored when a run starts, so a late ticker never keeps agents waiting. A person can lift one early with POST /api/runtime-pauses/:runtime/lift (for example after upgrading the plan), and GET /api/runtime-pauses lists the active ones for the Health screen.
- **Told apart from a rate limit.** A message with usage-limit or quota wording is a plan limit; "too many requests" and similar are transient and are retried by S3-2 without pausing anything (tested both ways).
- **Tests changed on purpose:** the old S0-8 test that used a limit to show a failed run blocking its task now uses an ordinary crash, and the S3-2 table no longer lists a plan limit among the "blocked at once" cases, because a limit now queues the task.

## 2026-11-13 (S3-2: retry, backoff and the fallback model)

- **Failures are sorted into four classes** (src/harness/failure.ts): transient (rate limit, overload, a 5xx, a network error), plan limit (a usage limit or quota), auth, and permanent (a crash, a bad config, too many turns, a timeout, a cancel). Only transient is retried. A plan limit and an auth error end the run at once, the first for S3-3 to pause the runtime and the second because only a person can fix a sign-in.
- **The retry plan:** after a transient error the run waits and tries again, three times (5 seconds, 20 seconds, a minute in the real server), and then once on the agent's fallback_model if it has one, then the task is blocked with the last error and what was tried ("after 4 attempts, the last on the fallback model"). The waits are a setting of the loop, not of the model, and tests inject their own so nothing sleeps.
- **A retry continues the same run and the same session.** It is one run row with the cost of every attempt added up, a `retry` event for each wait (what failed, how long, which model), and the session the first attempt reported passed to the next, so the agent resumes where it was. The attempts are visible in the run log.
- **The kill switch is looked at before and after each wait,** so turning it on during a backoff ends the retrying instead of starting a new attempt.
- **Retries are off unless configured:** without a retry setting a run makes one attempt, as before, so nothing existing changed. The server turns them on.
- **A caution I am leaving here:** a retry after a half-finished run can repeat a tool call that already worked. The os tools that write are safe to repeat (a proposal, a lead and a score all dedupe or replace; a comment would repeat), and the executors that act on the outside world are never retried by this: they run only after an approval is claimed, once.

## 2026-11-13 (S3-1: the reaper)

- **A run that stops heartbeating is failed and its task goes back.** src/harness/reaper.ts finds runs still running or queued whose last heartbeat is more than 2 minutes old and which this process is not running (a quiet run that is alive is never reaped), marks them failed with the reason, releases the task and puts it back to todo with its session id, so the next run resumes. A task that has now failed three times in a row (counting only the streak since the last run that did not fail) is blocked with the reasons instead. A task a person has since moved or cancelled is left as they left it. Running it again changes nothing.
- **The kill switch does not stop it.** Cleaning up after a dead run is always safe, so it runs while the switch is on.
- **It runs every minute in the ticker,** and the agent whose task was put back is asked to run again at once.
- **Restart recovery now uses it.** Before, a run found running at start blocked its task for a person to unblock. Now the first failure puts the task back to resume and only the third blocks it, which is what SPEC 14 says; the old test was changed to match. A task stuck in progress with no run at all is still blocked, because nothing says how far it got.
- **The session is saved the moment it is known** (it was saved only when a run ended), on the task and on the run. Without that, a run killed halfway had no session to resume from; this is the half of "kill a run halfway and it resumes" that needed fixing. Tested with a runtime that reports its session and then hangs: the session is on the task while the run is still going, and the next run is handed it.
- **Found while testing:** a full test run showed two database start-up tests and one timing test fail from load; each passes alone. They are the usual cost of starting many embedded databases at once on this laptop, not related to this change.

## 2026-11-12 (S1-5: settings, the kill switch and the send caps)

- **Two caps, both settings.** A rolling window, 30 emails in 5 hours by default (window_hours, window_cap), where follow-ups count like first emails; and a per-day cap, which I set to 100 by default because the answers fix the window at 30 per 5 hours but give no daily figure (a day holds a bit under five windows). ## 2026-11-12 (S1-3: the approval gate)

## 2026-11-12 (initdb watchdog, data safety, local model)

- **initdb runs under a watchdog on Windows.** On the laptop initdb stalled about one run in ten (the `postgres --check` bootstrap child sat idle), even on a fresh directory with nothing else running, and the library waits forever, so the server never started. Found with traces: `before initialise` printed and `after initialise` never did. Other platforms keep the library's `initialise()`.
- **Nothing in the OS ever deletes a database that holds data.** `runInitdb` refuses a target that has `PG_VERSION` or any file it did not create, and on a retry removes only what its own attempt made; an empty directory it was given stays. `startDatabase` wipes a cluster only when this server began creating it and never finished: a marker file (`first-start.marker`, in `DATA_DIR`) is written before initdb and removed after the credentials are written. A cluster with `PG_VERSION` and credentials that are missing, corrupt or the wrong shape is refused with instructions, never wiped; put the credentials file back and it starts with its data intact. This replaces the earlier S0-2 rule that wiped any cluster without a credentials file, which would have destroyed a real database if that file was lost.
- **`local-worker` is chosen only after the model passes the runtime conformance tests with tool calling.** No model is named for it before that, and the placeholder in `config/models.ts` is not a recommendation. ## 2026-11-12 (S0-13: heartbeats and turns)

- **The ticker remembers when it last asked each agent**, in memory for as long as the server runs. ## 2026-11-12 (S0-12: Windows process handling)

- **An npm `.cmd` shim is read, not run through a shell.** The resolver parses the shim and starts the program it forwards to: either a native `.exe` (this laptop's `opencode.cmd` does that) or `node` plus a script. A shell is the last resort for a shim it cannot read. Why: a shell adds a process, quoting rules and a second thing to kill. `claude` here is already a native `.exe`. `health()` and `start()` now quote through one function.
- **One way to start a command, in the runner, `health()` and `pnpm run doctor`.** A shell is the last resort, and then it gets one quoted command string, never an argument list (Node warns about that, DEP0190). Doctor used to start everything through a shell on Windows.
- **Cancel and timeout end the whole process tree on Windows** with `taskkill /pid <pid> /T /F`. `child.kill()` ends only the process we started, and a CLI runs its tools as children. Checked by a test that starts a fake CLI with its own long-lived child, cancels, and finds the child gone. Other platforms keep `child.kill()`.

## 2026-11-12 (S0-2: tenancy keys and policy)

- **Foreign keys cannot cross workspaces.** Every tenant table with an `id` gets `unique (workspace_id, id)`, and every foreign key between tenant tables is `(workspace_id, x_id) references t (workspace_id, id)`. Why: Postgres runs foreign key checks without row-level security, so a plain key lets a row in workspace A point at a row in workspace B. Cheap at schema birth, painful later. Goes beyond the original slice 0 block, so SPEC 11 was updated first. `members` has no `id`, so it keeps its plain key. `departments.lead_agent_id` gains a composite key too, added after `agents` exists. SPEC 11.
- **Policies use `nullif(current_setting('app.workspace_id', true), '')::uuid`.** On a pooled connection that has run `set_config(..., true)`, the setting reads as an empty string, not null, and a bare `''::uuid` raises an error instead of returning no rows. A test covers a one-connection pool. `workspaces` has no `workspace_id`, so its policy is on `id`. SPEC 11.
- **Three database roles.** The `initdb` superuser is used once at first start to create `conclave_owner` and `conclave_app`, then never again, and its password is not stored. The owner owns the tables and is used only for migrations and bootstrap. The app role serves requests with select, insert, update and delete only. If first start is interrupted before the credentials file exists, the half-made cluster holds no data and is wiped and made again. SPEC 11.
- **`conclave_owner` has `bypassrls`.** Under forced row-level security even the table owner sees no rows with no workspace set, so bootstrap could not ask "is there a local workspace yet?" or count workspaces. The owner is never on a request path (it is a short-lived connection for migrations and bootstrap), and the request role has no bypass. SPEC 11 says so.
- **No default privileges for the request role.** The grants migration names the twelve tables. A table added later is invisible to `conclave_app` until its own migration enables and forces row-level security, adds the policy and grants on it, and the tenancy test fails if a table skips that.
- **`pnpm db:migrate` starts the embedded database, applies migrations and stops.** The server applies the same migrations at every start. Checked by hand: a hard kill of the server's process tree leaves no Postgres behind, and the next start recovers.
- **Postgres is stopped with `pg_ctl stop -m fast`, not the library's `stop()`.** On Windows the library runs `taskkill /f /t` on the postmaster. That is a crash, not a shutdown, and it sometimes missed a child: a surviving `io_worker` was found after runs that passed, and in one loop of start, stop, wipe, restart the next start on the same directory hung (initdb's `--check` process stuck). The same path is Ctrl+C then restart of the real server. The fix keeps the same package and the same Postgres. Checked: ten rounds with zero Postgres processes left after every stop, three full test runs in a row, and a test that `postmaster.pid` is gone after a stop. If `pg_ctl` fails, it falls back to the library's kill. A start that goes wrong now fails with the last lines Postgres printed (the library rejects with `undefined`) and has a 90 second deadline. `CONCLAVE_DEBUG_PG=1` prints Postgres output live.
- **The database is UTF-8.** `initdb` on Windows chose `WIN1252` from the system locale, which cannot store emoji or most non-Latin text. Now `--encoding=UTF8 --locale=C --locale-provider=builtin --builtin-locale=C.UTF-8`, with a round-trip test. Also `--no-sync` on the brand-new cluster, which cut first start from about 14 s to about 5 s; an interrupted first start is wiped and rebuilt anyway.
- **Embedded Postgres is `embedded-postgres` 18.6.0-beta.19.** Spiked on Node 24.13 and Windows x64: it initialises, starts, runs PostgreSQL 18.6, and listens on 127.0.0.1 only. Port 54329, read from `PG_PORT`. Role passwords live in `DATA_DIR/secrets/db.json`, outside the repo.
- **One install script is allowed:** `@embedded-postgres/windows-x64`. I read it first: it only recreates symlinks inside its own package folder. esbuild stays denied. The policy stays on for everything else.
